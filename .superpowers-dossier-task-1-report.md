## Row-scoping

Genuinely row-scoped (single WHERE clause or an array-of-one call to an already-parameterized
helper whose OWN query narrows on that array), replacing `boardRows`'s whole-board join +
value/tier recompute entirely (safe because `factsInputFor` never reads a shape-dependent
`BoardRow` field):
- `players` identity, `WHERE id = playerId`
- `nflPlayerIdsFor(db, [playerId])`
- `preseasonProjectionsFor(db, stamp, [nflPlayerId])` (the player-scoped sibling of
  `preseasonProjectionsAsOf`)
- `currentSeasonSummaries(db, [playerId], …)` — its own `inArray(playerStatLines.playerId, …)`
  genuinely narrows to this one player.

Narrowed to the target's own position (not the whole board) for `lastSeasonStoriesFor` — a
genuine DB-level win, since its own `statLinesAsOfForLiveSurface` call takes a `playerIds` list
built off the `positions` map, so a smaller `positions` map shrinks that query's `WHERE … IN (…)`.
Passing the same narrowed `peerPositions` map to `usageTouchesAndTrendFactsFor` keeps its RANKING
math correct (both functions bucket by position internally via `rankWithinGroups` /
`pooledDiscoveryValuesByPosition`, so the other positions' rows were never entering this player's
bucket either way, narrowed or not) — but see the correction below: unlike
`lastSeasonStoriesFor`, this does **not** shrink `usageTouchesAndTrendFactsFor`'s own DB reads.

### Correction (review round 2)

The original version of this report and the module docblock overstated the win for
`usageTouchesAndTrendFactsFor`: its `discoveryFactsForSeason` call resolves through
`seasonContext` to `seasonScoring`/`seasonParticipation`/`seasonTeams`
(`projections/laws/populations.ts`) plus its own `seasonUsageAggregates`/`seasonSnapCounts`/
`seasonTeamPaceByTeam`/`incomingWinTotalByTeam`/`seasonActualWinsByTeam`
(`projections/laws/discovery-facts.ts`) — none of these eight readers takes a `playerIds`
parameter; every one of them scans the WHOLE season regardless of the `positions` map's size and
filters down to it only in memory afterward. Narrowing `peerPositions` keeps the rank output
correct but does not reduce this function's own query cost — it is a REMAINING WIDE READ, not a
closed one. The one exception inside it: `trendsFor`'s own `seasonYardsAndTargetsFor` calls DO
take a `playerIds` list (`discoveryFacts.keys()`, which reflects the narrowed input), so that one
sub-read genuinely shrinks.

## Reads that stayed board/team-wide (documented in the module docblock)

- `allPositions(db)` — every `nfl_players` id-to-position row; needed even for the position-narrow
  above, since "who else plays his position" requires knowing every player's position first. No
  player- or position-scoped query exists. Small table, not a stat read.
- `usageTouchesAndTrendFactsFor`'s own `discoveryFactsForSeason` reads — see the correction above;
  a genuine remaining wide read, not narrowed by the position filter despite taking it as an
  argument.
- `boardReasons(db, BOARD_SOURCE, PRODUCT_SEASON)` — no player-scoped variant in the store; read
  whole then indexed down to the one player.
- `propsLinesByPlayer(db, PRODUCT_SEASON)` — `loadArchivedPropLines` has no player filter; read
  whole then indexed down.
- `vegasWinTotalsByTeam` and `byeWeeksByTeam` — team-keyed, already small (32 teams), no
  team-scoped reader exists.
- `injurySnapshot(db)` and `newsForPlayers(db, [name])` — both already the smallest read the store
  offers: a single `LIMIT 1` snapshot row apiece, filtered down to one player in memory. Passing a
  one-element array to `newsForPlayers` narrows nothing at the DB level (its underlying
  `latestNewsSnapshotBody` has no `WHERE` on player at all) — reclassified here from "row-scoped"
  in the original version of this report, per review round 2.
