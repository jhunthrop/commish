  1. Add the new secret version.

The coordinator creates the instance, roles, databases and secrets and runs the restore; the code and workflows connect to it (Lane 20).

Public IP with no authorized networks: nothing reaches it by address, only through the Cloud SQL connection or the Auth Proxy, both of which authenticate with IAM. Automated backups at 08:00 UTC, 7 retained, with point-in-time recovery. Needs the Cloud SQL Admin API (`sqladmin.googleapis.com`).

No VPC, no TLS settings in the URL: the connection encrypts the leg to the instance. Dev and CI keep the TCP form (`localhost:5433`).

## The service alerts

`infra/service-alerts.sh` (bash, launch audit F1), beside `research-alerts.sh` and on its email channel: `apply` creates the uptime checks and the policies or brings each to the file and ends with `verify`, `verify` fails unless each is live, enabled and on the channel, and `apply --dry-run` prints every request `apply` would send and calls nothing. What the checks and policies are lives in `infra/lib/service_alerts.py`; the project, the channel and the API call in `infra/lib/monitoring.sh`, shared with `research-alerts.sh`. The coordinator applies it (`infra/service-alerts.sh apply`, then `infra/service-alerts.sh verify`); the agent does not run gcloud.

- Uptime checks every five minutes from three US checkers (Oregon, Iowa, Virginia), 10 s timeout, 200 expected: "Commish api readiness" `https://api.trycommish.app/readyz`, "Commish web front page" `https://trycommish.app/`, "Commish room readiness" `https://room.trycommish.app/readyz`. The services are checked at `/readyz`, which also pings the database: Google's front end answers `/healthz` on Cloud Run with its own 404 before it reaches the service. The checks also keep one `api` instance warm most of the time (Cloud Run keeps an idle instance about fifteen minutes), at request-billed cost.
- "Service api unreachable", "Service web unreachable", "Service room unreachable": two of the three checkers failing for five minutes.
- "Service api 5xx over 2%", "Service room 5xx over 2%": `run.googleapis.com/request_count` with `response_code_class = 5xx` over 2% of the service's requests, five-minute rates, held ten minutes (PromQL).
- "Service api p95 over 3 s": the api's p95 `request_latencies` over 3 s for ten minutes, counted only when the five-minute window holds at least 100 requests (`SLOW_P95_MIN_REQUESTS`): on a quiet hour the uptime checks' three requests and one 40 s ESPN connect would make that connect the p95, and at 100 the p95 passes 3 s only when at least five requests are slow. The room has no latency policy: a WebSocket is one request for the whole draft, so its latency is the session's length.
- Each policy auto-closes 30 minutes after its condition clears, so the next outage opens a new incident and emails.
- Cloudflare: there is no Workers error-rate notification on our plan. The zone error-rate alerts (Notifications > Add > "Advanced Error Rate Alert" or "Origin Error Rate Alert") are Enterprise only, so the web's alert is the uptime check on `/` above. A Worker's errors are read in the dashboard: Workers & Pages > `commish-web` > Metrics > Summary > Errors, and its logs under Observability (`observability` is on in `web/wrangler.jsonc`).
- After every deploy, `api.yml` and `web.yml` end with `infra/post-deploy-check.sh`: `/readyz` on the api and the room, `/` on the site, each 200 or asked once more after 30 s (the Worker reaching every edge, a new revision's cold start), else the job fails.

## When something breaks

The alerts email the founder at jhunthrop@yahoo.com, the one person paged; members write to `help@trycommish.app`, which is also where an incident is answered. **The web**: a bad run rolls back with one command, `infra/web-rollback.sh <previous run id>` (wrangler's Cloudflare login or a `CLOUDFLARE_API_TOKEN` with R2 write, and gh). It moves both pointers in R2 `commish-runs` to that run, `runs/early.json` (`runId`, with `finishedAt` and `publicAt` now, so it is already public) and `runs/latest.json` (`runId`), then runs `gh workflow run web.yml --ref main -f runId=<previous run id>`. The API's `/run` routes (the apps' run, Lane 185) follow `latest.json` within a minute, so the apps roll back with the site. Moving `latest.json` alone is undone within the hour: the hourly `publish` sets latest to early's run whenever they differ (`research/nightly/publish.py`), and the 30-past backstop rebuilds it. The next nightly that passes its gates moves both on again; a bad web commit is reverted on main (`git revert <sha>` and push, which deploys), because a dashboard rollback of the Worker is undone by the next hourly build. **The API**: list the revisions with `gcloud run revisions list --service api --region us-east1 --limit 5` and send all traffic to the previous one with `gcloud run services update-traffic api --region us-east1 --to-revisions <previous revision>=100` (the room the same with `room`); traffic stays pinned there, so after the fix deploys, `gcloud run services update-traffic api --region us-east1 --to-latest`. With the laptop's gcloud login lapsed, revert on main and push instead (`api.yml` redeploys). **A platform**: set its repository variable and redeploy the api, `gh variable set HOST_ESPN_ENABLED --body false && gh workflow run api.yml --ref main`; the switches (`api/internal/config/hosts.go`, read by `config.go`) are `HOST_ESPN_ENABLED`, `HOST_YAHOO_ENABLED` and `HOST_FFPC_ENABLED` for connecting and reading, and `HOST_WRITES_ESPN_LINEUP`, `HOST_WRITES_ESPN_CLAIM` and `HOST_WRITES_MFL_LINEUP` for the moves made from our screens (each write kill also needs its `app.host_write_accounts` rows deleted, above). Sleeper's and MyFantasyLeague's public league reads have no switch.

## Firebase (push), set up 2026-10-27

- Firebase is attached to the GCP project `trycommish` (display name Commish), with the `firebase.googleapis.com` and `fcm.googleapis.com` APIs enabled. FCM is free.
- Apps: Android `app.trycommish.android` (app id `1:467414876046:android:98ad321f58a41e3003eedf`) and iOS `app.trycommish.ios` (app id `1:467414876046:ios:0581accd1e94f08203eedf`). Their client config files (`google-services.json`, `GoogleService-Info.plist`) come from the Firebase Management API (`projects/trycommish/{androidApps,iosApps}/<id>/config`); the push lane places them in the apps.
- Sending: `api-runtime@trycommish.iam.gserviceaccount.com` holds `roles/firebasecloudmessaging.admin`, so the API sends through the FCM HTTP v1 API with its own identity; no key file.
- The server side (Lane 262, spec §5.3): an app registers its token with `PUT /devices/{id}/push` (its own device, the session scope; a token another member's still-active device holds is 409). Producers insert rows into `app.notifications` and never send. The Cloud Run job `api-notify` (`/api notify`, deployed by `api.yml` with `DATABASE_URL` alone mounted, on its own narrow configuration) catches the producer up (below) and drains the due rows every minute in season: rows claimed by lease, a run budget under the lease and untried rows released, FCM v1 with the runtime's identity (`FCM_PROJECT_ID`, default `trycommish`), a doubling backoff up to six attempts, a token removed only on FCM `UNREGISTERED` or APNs 410/`Unregistered`, and only devices used within the session's 30 days receive. Its Cloud Scheduler job `api-notify` (`* * * 1,2,9-12 *`, caller `research-runtime`, which `api.yml` grants `run.invoker` on the job) is in `infra/research-schedule.sh`, so `apply` creates it PAUSED: resume it by name. A resume after a pause (the season's start, an outage) catches the producer up over the last 24 hours of captures in its first run, so a day of status changes queues at once; a newer change for a player gives up an older unsent one, so each member hears each player's latest status once. The first run ever, with no mark, looks back 3 hours. Quiet hours (23:00 to 08:00 New York time until the member sends a zone) and one switch per kind ride on `GET/PATCH /me`.
- The first producer: after each hourly capture, `research.inseason --task capture-harvest` posts `POST /internal/notifications/starter-status` with `research-runtime`'s Google identity token (RS256, audience `https://api.trycommish.app`, from the metadata server). The call is advisory: it never fails the capture. The API verifies the token against `INTERNAL_CALLERS` (the service's alone; several are separated by spaces, never commas, because the deploy action splits its list on commas; default `research-runtime@trycommish.iam.gserviceaccount.com`), records the request in `app.notify_marks` and answers 202; nothing runs on the API. Each `api-notify` run, holding a transaction-level advisory lock (one process at a time), first catches the producer up when a capture landed after its mark's `done_through` or a request came after its last run began: every pair of readable injury captures since `done_through` (24 hours at most, 3 hours on a first run), one push per account, player and change, starters read from the league reads and directories the API kept (the job reads no host), a league whose kept read is over 36 hours old skipped and counted (`stale_leagues` on the produced line) because its lineup may have changed on the host since. The catch-up reads the captures after the mark by time (game days store up to four an hour) and stops at 20 s inside the job's 90 s task timeout; the drain claims for 45 s and sends nothing past 80 s. A newer change for a player gives up an older unsent one. Then it drains. The research jobs read the API's URL from the repository variable `COMMISH_API_URL` (https only; unset, the call is skipped with a line). Set it to `https://api.trycommish.app` once the API serving the route has deployed, then redeploy research.
- Push alerts (`infra/lib/service_alerts.py`, applied by `infra/service-alerts.sh apply`): "Push job error", any error line from `api-notify` (a failed catch-up, a failed drain, its exit), a log-match policy emailing at most once an hour. There is no alert on the absence of a producer run: it would need a log-based metric, which these scripts (Cloud Monitoring alone) do not create.
- APNs direct: `APNS_KEY_ID`, `APNS_TEAM_ID` and `APNS_KEY` (the .p8's PEM) in Secret Manager, added to `api-notify`'s `--set-secrets`, turn the APNs sender on (`APNS_TOPIC` defaults to `app.trycommish.ios`; `APNS_SANDBOX=true` for an Xcode build). The signed provider token is kept in `app.apns_provider_tokens` and reused for 50 minutes across runs (Apple refuses refreshes more often than every 20). Until the key exists an `apns` registration's rows are given up and logged. An iOS app that registers an FCM token instead (`platform: fcm`) is delivered through FCM once the .p8 is uploaded to Firebase, below.
- iOS delivery waits on the Apple Developer account: once it is approved, create an APNs auth key (.p8) in the Apple Developer portal and upload it in the Firebase console (Project settings, Cloud Messaging, Apple app configuration). That upload has no API.
