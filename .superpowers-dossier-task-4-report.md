## Where `PROP_MARKET_LABELS` ended up

Extracted to `src/capsules/prop-market-labels.ts` — a one-export, zero-runtime-dependency module (imports only `type { PropMarket }`). Reason: `capsules/render.ts` imports `PlayerFacts` from `capsules/facts.ts`, and `facts.ts` imports `createHash` from `node:crypto` (for `factsHash`) — a Node built-in that has no business in a client bundle. `@/capsules` is not on `eslint.config.mjs`'s `SERVER_ONLY_MODULE_GROUPS` blocklist, so `npx eslint` alone would not have caught a direct `books-module.tsx` import of `render.ts`, but the transitive `node:crypto` pull is a real bundler-time risk the lint gate does not cover. Rather than gamble on that, `PROP_MARKET_LABELS` moved to its own dependency-free file; `render.ts` now imports it (`import { PROP_MARKET_LABELS } from "./prop-market-labels";`), and `books-module.tsx` imports the identical map from the identical path — one label, never two copies that could drift when `PROP_MARKETS` gains a market. `render.test.ts` (20 tests) stays green untouched, since no test referenced the constant by name, only its effect on `booksNumbersLine`'s output.

## Judgment calls beyond the plan's literal prop lists

- **`RoleModule` takes a `position: Position` prop** in addition to `usage`/`trend`. The mandated format `"{pct}% · {POS}{rank} of {n}"` needs his own position, which no field on `PlayerFactsUsage`/`PlayerFactsRankedStat` carries — a rank object is position-agnostic by design (`rank.ts`'s own docblock). Documented in the prop's own JSDoc as a deliberate addition to the plan's two-prop shorthand, not an oversight.
- **`RoleModule.usage` and `SeasonStrip.story`/`BooksModule.books` are non-null props** (the CallCard/RangeRail idiom from Task 3: "keep props non-null by contract here"). `usage: PlayerFactsUsage | null` is the one exception — kept nullable so a wholly-untracked season (a rookie) falls through the SAME "not tracked for him" text path every individually-absent share already uses, rather than forcing Task 5 to special-case "no usage object at all" versus "usage object with every field null."
- **The trend delta's magnitude color is earned through `Stat`, never a hand-written `-mag-` class.** `magnitude-budget.source.test.ts` allows `-mag-` in exactly one file (`components/ui/stat.tsx`); RoleModule constructs an honest `StatComparison` (`percentile: 0.75` for a material rise, `0.25` for a material decline — both comfortably inside `Stat`'s own "good"/"weak" bands per `UI_CONFIG.stat.percentileFloors`, `population: "the position's own year-over-year spread"`, the real population `trend.ts`'s own materiality test judges against) and lets `Stat` pick the color. Verified: `data-magnitude="weak"` for a decline, `"good"` for a rise, and the design guard's own sweep still passes with zero new allowlist entries.
- **`SeasonStrip`'s "finish"/"receiving yards" facts print no position prefix** (just "{ordinal} of {qualifierCount}"), unlike `RoleModule`'s shares — the coordinator's own restatement of the SeasonStrip contract omitted a `{POS}` token where RoleModule's explicitly named one, and `SeasonStrip`'s own three-prop signature (`story, weeks, scoringLabel`) carries no position to prefix with in any case.
- **`SeasonStrip` reuses `SeasonBars` (`@/components/ui`) directly** rather than drawing a second chart — it already is "played weeks scaled to the max, missed weeks a flat hole, every column from week one," exactly the plan's own spec, and reusing it is the DRY choice the coordinator's "read your Task 3 patterns" note pointed at.
- **`StoryModule` renders each half (designation pill, season-ending sentence) independently**, returning `null` only when BOTH are absent — the original Task 4 plan text ("absent BOTH → renders nothing") rather than the shorthand restatement taken as "story null means the whole module is gone," since a current designation with no season-ending story (merely questionable this week) is a real, common state this module should still speak to.
